# Phase 7 Website Chat transport

Website Chat uses the existing `ChannelAdapter`, `InboundGateway`, universal event, batch, effect, and worker pipeline. The Phase 3 in-memory `WebsiteContractService` and `FakeWebChatAdapter` remain test fixtures under channel `web_chat_contract`; production uses `web_chat` and registers only `WebChatAdapter` in worker composition.

## Provision and embed

An agency actor with `channel.manage` opens `/businesses/{businessId}/web-chat`, selects a published agent ID, enters exact HTTPS origins, creates a disabled site, then enables it. A site and its `channel_connections` row share an ID. The public `pk_…` key may be embedded in a page. The agent must have a published active version before enablement. Disabling a site pauses its connection and revokes all visitor sessions. Changes are audited.

Browser code may import `WebChatClient` from `@agentos/website-sdk/client` and call `connect`, `send`, `poll`, and `disconnect`. The client keeps the bearer token only in memory and exposes the opaque visitor ID for optional first-party persistence. It sends no cookies. The service must be reached over HTTPS except for local development. The client exposes text and an optional consent-aware page context; file and image uploads are disabled and rejected by the server.

Public endpoints are `POST /api/web-chat/v1/bootstrap?site={publicKey}`, `GET/DELETE /api/web-chat/v1/session?site={publicKey}`, and `GET/POST /api/web-chat/v1/messages?site={publicKey}`. `OPTIONS` accepts only configured exact origins. `GET messages` supports an `after` ULID cursor and returns at most 100 messages plus conversation ownership. This polling transport reports `HUMAN_ACTIVE`, `HANDOFF_REQUESTED`, and other ownership states without making an AI reply after handoff. It has no WebSocket or push delivery; callers choose their polling interval and handle network failure/retry.

## Authority and durability

The signed 15 minute token carries session/site/business/agent/visitor/origin/expiry. Every call validates its HMAC, exact Origin, DB session, expiry, revocation, site configuration, channel connection, business state, and URL site key. The signing secret is server side only. Visitor IDs are random ULIDs; the DB stores an HMAC hash, not the raw ID. A row lock creates one customer, hashed channel identity, and conversation for a visitor session even under concurrent first messages. Refresh reuses that binding. Inbound message IDs are derived from session and caller idempotency key, then flow through the durable raw event and batch transaction. Different content with the same key is rejected. Per-session message/poll and aggregate site bootstrap counters live in PostgreSQL, work across app instances, and are purged by the worker's retention timer.

The adapter writes outbound text into scoped `messages` with a deterministic external ID. Retried execution and reconciliation find the same row. The adapter checks site readiness and `AI_ACTIVE` ownership before delivery. Unsupported image/file/reaction actions are skipped; `ReplyToMessage` targets only a customer message in the same conversation. Page context strips the query string, bounds the path and title, and excludes product/cart references without explicit consent; the normalized form is recorded on the inbound message. Public responses contain only visitor-visible text, sender, time, cursor, and ownership.

## Validation and limitations

`0010_great_mephisto.sql` adds `visitor_sessions.conversation_id` and durable `web_chat_rate_buckets`; no applied migration was edited. A fresh PostgreSQL database accepted every migration. `bun scripts/phase7-webchat-integration.ts` passed agency authorization, publication gating, exact origins, signature tampering, rate limits, tenant scope, visitor binding, duplicate detection, attachment rejection, page privacy, fake-model batch processing through the real adapter, outbound reconciliation, polling, handoff suppression, and revocation. The built Next.js server was also exercised over HTTP: CORS preflight, bootstrap, inbound, duplicate acknowledgement, polling, origin denial, and DELETE revocation passed. `bun run check` passed 74 tests and 404 assertions; `bun run admin:build` passed.

The HTTP drill uses a controlled local origin and fake model. It is not a live merchant-site/browser or production model acceptance test. Human staff reply transport in the client UI is not yet wired; ownership is visible to the visitor, while the handoff system prevents AI delivery. The visitor transport currently supports polling and text only. Rate buckets are retained up to the hourly worker cleanup and need a running worker. Live release also requires the shared Phase 7 operational and provider gates described in `phase7-progress.md`.
